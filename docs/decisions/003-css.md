# 003 — Styling: plain CSS, no Tailwind

Date: 2026-11-16. Status: accepted.

## Context

Phase 3 implements the owner-approved visual design (three PNGs in
`docs/ui-ux/`, transcribed in `docs/design/spec.md`) on the Phase 2 reader:
token-driven light+dark theme, serif/mono type system with self-hosted fonts,
restyled home/archive/post/tag/about/404, three new content nodes. Public JS
budget is ≤ 3 KB; single author; three stylesheets + tokens already in place
(`src/styles/tokens.css`, `base.css`, `article.css`).

## Options

1. **Plain CSS (tokens + two stylesheets).** Zero new runtime deps, full
   control of the 3 KB JS budget, every color/size/space/motion value already
   centralized in `tokens.css`. Design maps 1:1 onto custom properties.
2. **Tailwind.** Utility classes would replace the token files, but add a
   build-time dependency, a second source of design values (config + classes),
   and no benefit for a fixed two-theme design with no component reuse across
   projects.

## Choice

Plain CSS. Fewer deps fits the minimal brief; the spec's token table is
already a stylesheet in waiting.

Also recorded: no syntax highlighting (mock code blocks are uncolored mono;
spec 03 §7 ADR only if adopted), no View Transitions (not in mockups; motion
limited to hover/focus + `prefers-reduced-motion` kill-switch which already
exists).

## Consequences

- `src/styles/tokens.css` is the sole home of design values (spec 03 §2);
  acceptance: no hard-coded design values elsewhere — grep proves.
- If a second consumer (Phase 4 admin) needs shared components (buttons,
  pills, tables), keep them public-side only for now.
